## 3. Pull Request #33〜#35で補修した問題

### Pull Request #33: 音声の停止と復帰

音声機能の再開失敗を処理し、画面非表示時に再生中・予約中の効果音を停止し、復帰後に古い音を再生しないようにした。初期設定「なし」と、得点、反射、ランキング、共有は変更していない。

### Pull Request #34: 反射元の二重通知

壁またはガラスから作られた反射波へ、反射元を処理済みとして引き継ぐようにした。同じ1回の接触から反射通知と効果音を二重に出す直接経路は解消した。

### Pull Request #35: 3タップ後に10秒を待たず終了する

Pull Request #30の監査時点では、3タップ後に波が0件になると10秒の締切前でもRESULTへ進んでいた。

Pull Request #35で終了条件を残り時間だけへ分離した。自動試験では5.8秒と0.001秒で継続し、0秒と負の残り時間で終了する。iPhone実機での10秒終了は未確認である。Phase 4Cには固定更新、単調増加時計、画面非表示時の締切処理が残る。

Pull Request #33〜#35は、いずれもGitHub ActionsのNode.js 18、20、22で合格した。

## 4. 後続Phaseへ残す重要問題

### Phase 4C: 画面更新間隔で得点が変わる

現行の可変時間更新では、同じ候補C、同じ3タップ、同じ5秒でも得点が一致しない。

```text
60分割: 24,525点
120分割: 24,012点
```

命中を各更新時点で採点するため、更新間隔によって命中誤差が変わる。Phase 4Cの固定更新と、60Hz相当・120Hz相当の比較試験で解消する。正式ランキングを再開する前の必須条件とする。

### Phase 4A: 同じ面を再判定できる距離が未定義

正本文書の「十分な移動距離を消費するまで同じ面で再反射させない」には、距離の数値または計算規則がない。Phase 4A開始前に契約を決め、決定ログへ記録する。

監査では、反射判定片幅9論理pxの2倍である18論理pxを候補とした。ただし、この監査文書だけでは正式決定しない。`DECISION_LOG.md`と`docs/SPEC_v3.md`を更新してから実装する。

Pull Request #30の監査時点では、反射子波が半径1、年齢0、空の面履歴で作られ、左壁から20論理pxの位置を使った固定入力診断で同じ左壁へ即時再反射した。Pull Request #34で反射元を処理済みとして引き継ぐ最小修正を入れたが、再判定距離の正式契約と親子波の面履歴は未実装である。

### Phase 4A: 有限線分の外側でも反射する

現行のガラス判定は、線分への射影位置を端点へ制限した後も法線方向の距離だけを使うため、端点から離れた延長線付近で反射できる。配置分析は有限線分までの実距離を前提としており、本番判定と分析が一致していない。

候補Cの`glass-c1`では、論理座標`[208, 186]`のタップが線分外の延長線付近で反射することを固定入力診断で確認した。

壁とガラスを有限線分として扱い、線分外へ射影される場合は近い端点までの実距離で接触を判定する。線分の延長線へ近いだけでは反射させない。

### Phase 4A: 反射系列と波IDが更新・resetへ依存する

公式配置の根波1つを同じ時間だけ進める固定入力診断では、反射イベントが60分割で37件、120分割で36件となった。得点だけでなく反射系列自体が更新幅へ依存している。Phase 4Aでは同じ物理step列の反射系列を決定的にし、Phase 4Cでは60Hz相当・120Hz相当の描画間隔から同じ固定step列と反射系列になることを確認する。

また、波IDの連番が全Worldで共有されてreset後に同じ番号へ戻らない。子波は年齢0から寿命をやり直し、波配列の走査中に子を追加しながら24波超の先頭を削除するため、未処理波を飛ばす可能性がある。Phase 4Aでは、同じ物理step列の反射イベント系列、reset後のID再現性、寿命継承、配列上限時の処理順を自動試験へ含める。

### Phase 5: 停止中の旧ランキング契約

停止中の通信関数には、旧`CLIENT_VERSION`と`Authorization: Bearer`が残る。Pull Request #29で送信関数の入口から拒否するため、停止中は通信しない。

Phase 5では、正式な接続先、`apikey`だけを使う契約、v3の版、旧記録との分離をまとめて確認する。停止解除だけを先に行わない。

### Phase 7: 画質によって見えない波が判定される

Worldは最大24波を判定するが、WebGLは画質により先頭7、10、12波だけを描く。Canvas 2Dは全波を描く。

判定される波を画質だけで非表示にしない。画質低下は粒子、解像度、残像などへ寄せ、少なくとも簡略表示で全判定波を見せる。

### Phase 7D: WebGL途中失敗後のCanvas切り替え

同じcanvasでWebGL contextを取得した後に初期化が失敗すると、同じcanvasから2D contextを取得できず、Canvasフォールバックも失敗する場合がある。

Phase 7Dでcanvasの置換または別canvasによる安全な切り替えを実装する。

### Phase 6: 共有と小画面

- 練習結果の共有文が公式結果と区別できない。
- HOME共有が0点の結果文になる。
- 画面全体のsafe-area対応は未完了である。

共有文、RESULT導線、safe-areaはPhase 6でまとめて修正する。

### 練習配置

練習用ガラス片は終点を論理画面内へ制限していないため、一部が画面外へ出る可能性がある。候補Cの公式配置には影響しない。練習配置の変更は、従来ランダム規則を維持するPhase 3Cとは分けて判断する。

## 5. G3の残り

G3の「同じ入力で同じ結果」は、同じタップと同じ物理step列での再現性を指し、自動試験で確認済みである。60Hz相当と120Hz相当のように物理step列が異なる場合の一致は、Phase 4Cの固定更新とG4で解消する。

自動試験だけではG3を完全通過にしない。次をiPhoneで確認する。

- 候補Cの端側ガラスを識別できる。
- HOMEの公式・練習カードを操作できる。
- 公式から練習、練習から公式へ切り替えられる。
- 再挑戦とモード再選択で前回盤面を次の配置と誤認しない。

端側ガラスが見づらい場合は、Phase 4Aへ進まず候補Dの比較へ戻る。

320×568相当のローカルChromiumでは、rootと`dist`の両方で公式・練習・公式の往復、名前保持、不透明なHOMEとCOUNTDOWN、通信0件、ページエラー0件を確認した。この結果はiPhone Safariの実機確認へ置き換えない。
