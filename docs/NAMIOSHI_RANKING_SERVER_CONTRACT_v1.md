# namioshi サーバーランキング契約 v1

> 現行Draftの契約値: `namioshi-v3.4.0-official005` / `namioshi-v3-reflection-tap-004` / `prelaunch-v4` / 0〜11200点。旧6回・6480点および旧v3の記録は歴史資料であり、新seasonへ移行しない。

状態: 未適用・未有効化

基準: `main` の Pull Request #46 統合後（`2ceb5a4`）

## この変更の目的

ブラウザ側だけでなく、サーバー側でも`namioshi`の送信値を確認する。ただし、現在のゲームは入力記録をサーバーへ送って再計算していないため、この契約を競技性の証明には使わない。

今回のSQLは、既存作品の共有ランキング記録を変更せず、`private`スキーマへ`namioshi`の記録を分けて保存する提案である。SQLファイルはGitHubへ登録するが、Supabase本番へは適用しない。

## RPC契約

既存の4引数版`submit_score`は残す。7引数版は専用RPC名`submit_namioshi_score_v1`で追加し、同名の関数を引数だけで重ねない。Supabase公式資料では、関数名の重複（オーバーロード）はRPCで扱えないためである。

```json
{
  "p_display_name": "プレイヤー名",
  "p_game_slug": "namioshi",
  "p_score": 1230,
  "p_client_version": "namioshi-v3.4.0-official005",
  "p_play_id": "端末内で一度だけ作る識別子",
  "p_rule_version": "namioshi-v3-reflection-tap-004",
  "p_season": "prelaunch-v4"
}
```

サーバーは次を確認する。

- ランキング設定が有効か
- `game_slug`が`namioshi`か
- 名前が1〜20文字か
- スコアが0〜11200点の整数か（経路10800点＋反射波タップ最大400点）
- 許可したクライアント版、ルール版、seasonか
- `play_id`が安全な文字だけで1〜128文字か
- 同じ`play_id`の再送が同じ内容なら、同じ結果を返すか
- 同じ`play_id`へ別の内容を送った場合は拒否するか
- 同じ名前からの送信回数が設定値を超えていないか

既存の共有4項目版や既存作品のデータは、この提案の対象外である。

配置版`namioshi-v3-layout-study-001`は座標の履歴識別子であり、ランキングの競技ルール版には使わない。波速110と二段階得点台帳の新記録を旧波速165の記録と混ぜないため、client version、rule version、seasonを同時に分離する。この契約とSQLは未適用で、ランキングは無効のままである。

## RPC名の安全条件

`public.submit_namioshi_score_v1`だけをこの提案の新規RPCとして追加する。既存の`public.submit_score`と同じ名前へ別引数の関数を追加しない。

参考: https://supabase.com/docs/guides/database/functions

## 自己申告と競技性

このv1の`verification_status`は`self_reported`で固定する。これは「サーバーが受け付けた自己申告記録」であり、「不正できない競技記録」ではない。

頻度制限は正規化した表示名をキーにする基本的な送信抑制であり、利用者の本人性や不正防止を証明するものではない。

競技ランキングとして公開するには、別工程でサーバー発行のプレイ情報、入力時刻列、決定的な再計算、異常時の隔離を設計する必要がある。ユーザーが自己申告ランキングを採用するか、競技版を設計するかを決めるまで、送信と表示は有効にしない。

## 有効化条件

次を別々に確認するまで、クライアントの`enabled=false`を維持する。

1. このSQLを非本番で構文・拒否条件・同一`play_id`の冪等性・頻度制限まで確認する。
2. 既存作品のRPCと記録へ影響がないことを確認する。
3. 自己申告か競技版かを決める。
4. `public.games`への登録、ランキング取得、結果画面接続を別の変更として確認する。
5. ユーザーが本番適用と限定疎通を明示承認する。
