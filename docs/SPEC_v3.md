# namioshi v3 仕様

この文書はv3ゲーム仕様の正本である。2026年8月の実機確認を受け、時間、タップ数、反射板表示、得点台帳の契約を更新した。

## 現行競技ルール（Draft PR）

現行mainの競技ルールは `namioshi-v3-reflection-tap-004`、client versionは
`namioshi-v3.4.0-official005`、seasonは `prelaunch-v4` とする。1プレイは30秒、
根の波は最大10回、波速は110論理px/秒、波の寿命は3秒である。旧6回・6480点の
端末ベストやランキング記録は新ルールへ移行せず、別キー・別seasonとして扱う。

## 状態遷移

目標状態は `BOOT`、`HOME`、`RULES`、`COUNTDOWN`、`PLAYING`、`RESULT`、`ERROR` とする。内部状態として必要なら `SUSPENDED` を追加してよい。`LOADING` は、実際に待つ必須素材がある場合だけ使う。固定時間の見せかけの `LOADING` は使わない。

基本遷移は `BOOT` → `HOME` → `COUNTDOWN` → `PLAYING` → `RESULT` とする。`RULES` は `HOME` から開き、閉じると `HOME` へ戻る。`ERROR` は、WebGLとCanvas 2Dの両方を初期化できない場合など、ゲームを継続できない時だけ使う。

カウントダウンは `3: 600ms`、`2: 600ms`、`1: 600ms`、`START: 400ms` とする。カウントダウン中の二重開始を防ぐ。HTMLのidは全画面を通して一意にする。

`PLAYING` は残り時間が0になった時だけ `RESULT` へ進む。10回のタップを使い切った場合や、画面上の波が0件になった場合も、開始から30秒が経過するまでは終了しない。

競技ルール版ごとの初回プレイでは、時間制限なしの案内を1回だけ表示する。案内では反射板へ波を当てる操作と、各タップ・各ビーコンで最高1経路を判定した後に同一経路を抑制する規則を示す。反射板へのガラス反射を1回確認するまでは本番開始ボタンを無効にし、確認後に画面状態とボタン文言を更新して本番へ進める。案内からHOMEへ戻る操作は成功前でも使えるが、成功前に案内を完了扱いにしない。案内を終えるまで公式または練習の30秒プレイは開始しない。

## HOME

最低限、正式タイトルnamioshi、1～2行の短い説明、ランキング名入力、ゲーム開始、ルール説明、ゲームをシェア、実験場へ戻る、音のON/OFF、ランキング名が公開されることの説明を置く。開始時は入力欄をblurし、iPhoneのキーボードを閉じてからカウントダウンへ進む。

## ゲーム内部座標

ゲーム内部は360×640の固定論理座標を使う。端末表示では、縦横比を保って拡大縮小する。余った領域は水面背景で埋める。ゲーム領域を切り取らない。

入力座標は次の順で変換する。

1. canvasの画面上の位置を取得する。
2. 表示倍率と余白を除外する。
3. 360×640の論理座標へ変換する。
4. ゲーム領域外の入力を拒否する。

画面サイズが変わっても、同じ公式配置と同じ論理座標タップなら同じ結果になることを要求する。

## 入力

- Pointer Eventsを使う。
- `pointerdown` へ統一する。
- `touchstart` を重複登録しない。
- `isPrimary` が真の入力だけ受ける。
- `PLAYING` 中だけ受ける。
- UI上のタップをゲーム入力にしない。
- 最大10回とし、11回目以降は無視する。
- 1入力から根の波を1つだけ作る。
- `pointercancel` を処理する。
- マルチタッチをゲーム操作に使わない。
- ピンチズーム、ダブルタップ拡大、横スクロールを抑える。
- リンクと入力欄は必要な標準操作を残す。

入力時刻の決定性:

- プレイ開始時の単調増加時計を入力列の基準にする。入力は論理座標、時刻、同時刻内の内部採番順でキューへ保存する。
- プレイの入力区間は `[開始時刻, 開始時刻+30秒)` とする。締切時刻ちょうど、および締切後の入力は受け付けない。
- 入力は入力時刻以上となる最初の固定境界へ到達した後、直前の固定stepを実行してから適用する。同時刻の入力は保存順で適用する。画面休止により次の固定境界が締切後へ移り、締切前に受理した入力が残った場合だけ、締切終端でその入力を保存順に適用する。この終端適用では物理を進めない。
- 1描画あたりの物理更新は最大3stepとするが、未処理の累積時間は捨てずに後続描画へ持ち越す。締切をまたぐ描画では締切時刻までを供給し、同じ締切時刻を使って未処理stepを精算してから一度だけ`RESULT`へ進む。
- 画面非表示または`pagehide`へ移る時は、その時点までの可視時間を固定更新へ渡してから物理更新を停止する。未処理の可視時間と未適用入力は保持し、復帰時に固定境界と入力の適用時刻を非表示時間分だけ後ろへ移す。これにより非表示時間を物理へ加えない。締切時計は進むため、移動後の適用時刻が締切以上になる入力は破棄し、締切未満に残る入力は固定境界または締切終端で一度だけ適用する。
- 30秒締切の精算を開始した後に画面が非表示になった場合は、締切までに積み上がった残りstepを破棄しない。復帰後も同じ締切時刻で最大3stepずつ排出し、すべて終えてから`RESULT`へ進む。精算開始前に非表示となり、そのまま締切を越えた場合も、非表示前に積み上がった可視時間だけは精算する。この時、固定境界と入力時刻を非表示開始から締切までの分だけ後ろへ移し、締切後の非表示時間は加えない。移動後の入力時刻が締切以上になる入力は破棄する。`visibilitychange`と`pageshow`が同じ復帰を通知しても二重に時刻を移さず、復帰通知内ではstepを排出しない。復帰後の残stepは描画ループで排出する。
- 締切までの固定stepを処理した後、締切未満で受理済みの入力が残る場合は、物理を進めず締切終端で一度だけ適用する。続いて、固定stepで観測済みの最小`error`候補を一度だけ確定してから`RESULT`へ進む。物理を30秒より先へ進めず、終端入力を含む未到達の波から新しい候補を作らない。その後キューを空にし、次のプレイ開始時に時刻・内部採番順・締切状態を初期化する。

## モード

公式モードはランキング対象であり、全員が同じビーコン、反射板、初期速度、配置条件で競う。同じclient versionでは同じ条件とし、ランダム配置を使わず、結果確定後に1回だけ送信する。

練習モードはランキング対象外であり、ランダム配置を許可する。Supabaseへスコアを送らず、結果画面に「練習結果」と表示する。公式と練習のモード切り替えは現行実装に含める。

練習モードのランダム配置は決定的なseedを使い、反射板の両端をゲーム盤内へ収める。反射板の端点はx=18〜342px、y=90〜622pxの範囲に置き、各反射板と各ビーコン中心の距離は28px以上とする。候補を最大96回試し、候補が尽きた場合は同じ制約を満たす固定候補へ切り替える。公式配置とこの練習配置の制約は混ぜず、公式の座標・指紋は変更しない。

## 波の識別

各プレイヤータップに `rootTapId` を付ける。各波は最低限、`waveId`、`rootTapId`、`parentWaveId`、`originX`、`originY`、`previousRadius`、`radius`、`width`、`speed`、`age`、`lifetime`、`energy`、`reflectionDepth`、`reflectedBy`、`reflectionPath`、`surfaceHistory`、`emittedSurfaces`、`hitCandidates`、`finalizedHits` を持つ。

反射回数は最大2回とする。同じ波から同じ面への子波は1回だけ作り、同じ祖先経路では同一の壁またはガラス片を再使用しない。反射元を `surfaceHistory` へ、波自身が送出済みの面を `emittedSurfaces` へ記録する。旧18論理ピクセル再判定距離は、この有限経路契約で置き換え、現行仕様には使わない。

反射波の得点候補は、鏡像発生源からビーコンへ線を引くだけでは確定しない。`reflectionPath` を最後の反射面から逆順にたどり、すべての交点が各有限線分の区間内にあり、面の順序が正しい場合だけ候補にする。有限線分の延長線だけを通る経路と、同じ面を再使用する経路は拒否する。端点は交点係数0または1の許容誤差内だけ認める。

1回の固定step内で反射面を横切った場合、接触半径と接触時刻を求める。子波は接触半径からstep終端半径までを同じstep内で処理し、その範囲に2面目の接触や命中があれば取りこぼさない。新規子波の生成時点で次面の仮想最短半径をすでに越えていても、その面の先に有限経路として有効な接触点が残り得るため、未処理面を潜在経路から除外しない。得点は全有限交点を逆順検査して確定する。寿命判定はstep終端の年齢ではなく接触時刻で行い、寿命内の反射・得点を処理した後、寿命に達した親子波をstep終了時に残さない。

壁4面と反射板4面、反射深度2、同一面再使用なしから、1根波の構造上限は65波、10根波では650波とする。この値は性能目標ではなく、正規入力の経路を上限処理で黙って捨てないための故障検知上限である。

競技ルール`namioshi-v3-reflection-tap-004`の波速は110論理px/秒、波の寿命は3秒とする。1回の更新が寿命をまたぐ場合、移動、反射、得点を残り寿命までに制限し、3秒を越えた処理を行わない。移動中のビーコンとの判定もフレーム末尾ではなく寿命時刻の位置を使い、浮動小数の端数で次の固定stepへ波を残さない。

## 反射とエネルギー

初期エネルギーは `1.0` とする。壁反射後は直前のエネルギー×`0.72`、ガラス反射後は直前のエネルギー×`0.84` とする。2回反射後も同じ規則で減衰する。

エネルギーは、波の明るさ、波の帯の太さ、残像、ビーコンへ与える見た目上の揺れへ反映する。エネルギーが低いことだけを理由に、得点判定位置をずらさない。

## 得点契約

v3の得点候補値の初期契約は、直接波20点、壁で1回反射100点、ガラスで1回反射180点、2回反射300点とする。

命中精度:

```text
accuracy = clamp(1 - error / hitBand, 0, 1)
```

候補得点:

```text
candidateScore = round(baseScore * (0.8 + accuracy * 0.4))
```

得点候補は次の順序で二段階に絞る。

1. 同じ `rootTapId` と同じ `beaconId` の組み合わせでは、最も高い `candidateScore` だけを根タップ台帳へ残す。同点候補の代表は`candidateScore`降順、`reflectionDepth`降順、`error`昇順、`waveId`昇順で一意に決める。この段階で落ちた低得点経路は、別の新経路であっても経路台帳へ進まない。
2. 根タップの波群がすべて寿命を終えた時、または30秒締切で、その根タップを確定する。確定済みの根タップ台帳から、`beaconId`と順序付き反射面列が同じ経路ごとに最高候補1件だけを経路台帳へ残す。直接波の面列は`direct`と明示する。壁→反射板と反射板→壁は別経路とする。

第一段階を通過した新しい有効経路は候補得点を加え、既存経路の高精度更新は新旧候補の差額だけを加え、同点以下の繰り返しは0点とする。確定済みの根タップは後から変更しない。経路台帳の再構築で総得点を減らさず、総得点、内訳合計、経路台帳合計、画面へ通知した加点合計を一致させる。同時確定の通知は1件へ集約し、新規・更新・発見済み件数、合計加点に加えて、集約対象の候補種別数と実際に加点した種別数を別々に持つ。画面には加点種別の件数を「経路」として表示し、加点0の既知通知では候補種別を表示する。同時確定の表示に添える判定と反射種別は、集約得点全体ではなく最高候補の代表値であることを「代表」と明示する。長い通知は狭い画面で折り返す。

命中帯へ入った候補は、固定step列の中で最小の`error`を保留する。波が命中帯を抜ける時、寿命の最終sliceへ到達した時、または30秒締切までの固定stepをすべて処理した時に、一度だけ得点台帳、ビーコンの揺れ、命中通知へ確定する。締切確定では波、ビーコン、反射を追加で進めない。`error`が許容誤差内の完全一致だけは、その固定stepで直ちに確定する。これにより最初に帯へ入った時点の精度で固定せず、同じ波・ビーコンの命中通知を多重発火しない。

経路更新の例:

- 以前の最高候補: 20
- 新しい候補: 174
- 追加点: 154

公式スコアでは、全体コンボ倍率を使わない。経路のhard ceilingは `10タップ × 3ビーコン × 2回反射の最大候補360点 = 10800点` とする。さらに、反射後の可視弧をタップした技能ボーナスを根波ごとに1回、深度1は10〜20点、深度2は20〜40点まで加え、技能上限は400点、総hard ceilingは11200点とする。追加の経路台帳は得点を増やさず、技能台帳は経路台帳と分離する。11200点は連続座標・連続入力時刻における公式配置の実到達最大を意味しない。

反射波タップの判定は、反射深度が1以上で有限`reflectionPath`を持つ活動中の波だけを対象とする。タップ地点を波の円周へ射影し、射影点が有限反射経路上にあり、半径誤差が18論理px以内なら成功候補とする。誤差0を精度1、誤差18を精度0として、深度1は`round(20 * (0.5 + precision * 0.5))`、深度2は`round(40 * (0.5 + precision * 0.5))`を加点する。同じ`rootTapId`の重複タップ、同じ波の連打、反射前の直接波、有限経路外の弧は加点しない。根波の10回上限は消費せず、ラウンド全体で最大10件とする。

未使用で寿命内の有限反射弧には、タップ対象を見つけるための淡い黄色の補助表示を重ねる。この表示はWebGLとCanvas 2Dで同じWorld判定を使い、技能ボーナス取得後、根波確定後、寿命終了後は消す。補助表示は得点、判定範囲、波速、物理、台帳を変更せず、有限反射弧の形を隠さない。

## ビーコン

ビーコンは3個とする。公式モードでは初期位置と動きが固定で、端末サイズに依存しない。波が通過した時だけ短く揺れ、速度へ際限なく力を足さず、ばねと減衰で基準軌道へ戻る。見た目と当たり判定中心を一致させ、色だけで状態を伝えない。

基準位置・基準速度と、命中による一時変位・一時速度を分ける。命中時の一時速度加算は22、一時速度上限は48、一時変位上限は12論理ピクセル、ばね係数は36、減衰係数は10とする。命中によって基準速度を変更しない。

## 公式配置

現行公式配置は候補C「開港型」、配置IDは`candidate-c-open-harbor`、配置指紋は`fnv1a-fc71e804`、配置版は`namioshi-v3-layout-study-001`、競技ルール版は`namioshi-v3-reflection-tap-004`とする。配置比較時の波速165によるsnapshotとSVGは歴史資料として上書きせず、現行の波速110と二重台帳は別の戦略分析で管理する。以下は採用時に完了した選定手順の履歴である。

1. 3つ以上の公式配置候補を作る。
2. 同じ3タップ候補で自動検査する。
3. 直接波だけで高得点になりすぎないことを確認する。
4. 壁反射とガラス反射を使う意味があることを確認する。
5. iPhone SE級でビーコンとガラスが重なりすぎないことを確認する。
6. 人が実際にプレイして1つを選ぶ。
7. 公式配置ID、指紋、配置版を固定する。

## プレイ中の目的・得点・待機表示

プレイ中の凡例の上部へ、次の目的表示を常時置く。ビーコンへ波が重なった時は物理接触の確認と得点台帳の精算を同じ瞬間とみなさず、画面上でも分けて示す。

反射した波の輪は、通常の根波を出すタップとは別に狙ってタップできる。成功時は「反射波タップ：+N（判定・深度）」を表示し、根波ごとに1回だけ加点する。反射波タップは音や色がなくても、凡例・RULES・結果内訳のテキストで意味と点数を確認できるようにする。

- 通常時: 「目的：波をビーコンに重ねる。反射板経由は高得点です。」
- 初回案内時: 「案内：反射板に当てて波の向きを変え、白いビーコンへ重ねてみましょう。」
- ビーコン説明: 「白く光る点。波が重なると命中し、精算時に得点が確定します」

10回のタップを使い切った後は、入力回数の上限に達したことと、30秒までは結果を待つことを表示する。波が残っている場合は「波の結果を待っています」、波がなくなった場合は「波も消えました」と表示する。どちらの場合も、表示追加だけで`RESULT`へ早期遷移させない。

RULESでは、ビーコンに波が重なると命中し、反射板に当てるだけでは得点にならないことを明記する。基準点は直接20点、壁100点、反射板180点、2回反射300点で、命中精度により候補点が変動する既存の得点契約を説明表示へ反映する。命中確認は接触時、得点は波の精算時に「得点確定」として表示する。

練習モードの入口では、30秒・10タップ・反射経路の練習・ランキング外であることを表示する。ランダム配置、配置制約、ランキング送信なし、公式と同じ得点契約は維持する。

## 水系効果音

効果音は初期設定でオフのまま、HOMEで有効化した利用者にだけ再生する。タップは「水面の波紋」、壁・反射板は「水面で返る波」、ビーコン命中は「小さな水しぶき」、正の得点確定は「水滴の上昇音」、RESULTは「静かな水面へ戻る音」として、低音量の短い合成音を既存判定音へ重ねる。音が使えない環境でも、命中確認・得点確定・待機状態はHTML表示だけで理解できる。画面非表示時は既存の音声停止契約を維持する。

目的・得点・待機の文言は色や音だけに依存せず、HTMLテキストとして表示する。狭い画面では折り返しを許可する。実ブラウザ、iPhone・iPadでの読みやすさは別の未確認項目として扱う。

## 端末内保存

保存候補は `namioshi.displayName`、`namioshi.bestScore.{OFFICIAL_RULE_VERSION}`、`namioshi.playCount`、`namioshi.settings.sound`、`namioshi.lastClientVersion`、`namioshi.guide.completed.{OFFICIAL_RULE_VERSION}` とする。競技ルールが変わった場合、端末ベストと初回案内の完了状態を旧ルールから引き継がない。旧キーの値は削除しない。実際に保存していない場合、「保存されました」と表示しない。未送信スコアを自動で後日再送信する機能は、二重送信対策が決まるまで実装しない。

## シェア

シェア文の正式形は次とし、文末は必ずゲームURLにする。

```text
namioshiで {score}点！
反射する波をビーコンに重ねた。
https://chameleonjp.codeberg.page/namioshi/
```

順序は `navigator.share`、クリップボードコピー、手動コピー用テキスト表示とする。共有画面をキャンセルしただけの場合、勝手にコピーへ切り替えない仕様を検討事項として残す。

## ランキング契約

送信先:

```text
POST {SUPABASE_URL}/rest/v1/rpc/submit_score
```

ヘッダー:

```text
Content-Type: application/json
apikey: {SUPABASE_PUBLISHABLE_KEY}
```

Publishable keyを `Authorization: Bearer` へ入れない。

本文:

```json
{
  "p_display_name": "プレイヤー名",
  "p_game_slug": "namioshi",
  "p_score": 1230,
  "p_client_version": "namioshi-web-3.0.0-official001"
}
```

禁止事項は、secret key、service_role key、`public.game_scores` への直接INSERT、独自のゲーム専用RPC、共通 `submit_score` RPCの置き換え、Publishable keyの実値をREADME・仕様書・コミット・PR本文・完了報告へ転記すること、サーバー応答全文やキーを画面またはconsoleへ出すこと。

送信条件は、公式モードの結果だけ、`RESULT` を先に表示する、1プレイにつき1回、10秒程度のタイムアウト、`playId` で古い通信結果を無視、練習では送らない、通信失敗でゲーム結果を失わないこと。状態は未設定、送信中、成功、失敗を持つ。

Supabase URLとPublishable keyは、作業環境で提供されている正式値を確認する。値を推測しない。今回の文書作業では、コードの値を変更しない。

未確認事項として、現在の正式Supabase URL、Publishable keyとURLが同じプロジェクトのものか、`submit_score` の実RPC疎通、`public.games` へのnamioshi登録、現在の旧ランキング件数、v3スコアを旧ランキングと分ける方法、実験場トップの登録方式、詳細ランキングの登録方式を分けて扱う。

## WebGLとCanvas 2D

純粋WebGLを本命描画として維持する。Canvas 2Dを正式なフォールバックとして維持する。ゲームロジックは描画方式に依存させない。描画側は、ゲーム状態を受け取り、表示するだけにする。

得点判定する波は、HIGH、MID、LOW、Canvas 2Dのすべてでプレイヤーが認識できる形で表示する。品質を下げる場合は、解像度、粒子、背景装飾から調整し、得点対象の波を波数上限で隠さない。有限経路だけが有効な反射波は、`traceReflectionPath`と同じ契約で有効な弧だけを示し、無効な全円が命中するように見える状態を公開しない。

WebGLでは、シェーダー作成失敗、プログラムリンク失敗、バッファ作成失敗、WebGLコンテキスト消失、WebGLコンテキスト復帰、高解像度の負荷、描画資源の破棄、画面サイズ変更、画面回転、低性能時の品質低下を考慮する。コンテキスト消失中は可視時間を精算して入力と描画を止め、復帰時に資源を再初期化する。復帰または描画中のWebGL処理に失敗した場合は、新しいcanvasへ差し替えてCanvas 2Dへ切り替え、World、得点、入力キューを保持する。ブラウザ名や端末名だけで描画方式を決めず、必要な機能を実行時に確認する。

Three.jsへ移行する場合は、別作業で見た目、入力反応、iPhone SE級のフレーム時間、連続再挑戦、WebGLコンテキスト復帰、ビルドの保守性、Canvas 2Dへの切り替えを比較する。Three.jsを使うこと自体を品質の証明にしない。

## 視覚表現

目標は、暗い水面を上から斜めに見た2.5D表現である。

- 水面: 青黒、中央を少し明るくする、画面端は暗くする、細かい常時波を2層まで使う。
- 直接波: 水色、細め、残像は少ない。
- 壁反射: 青紫、直接波より残像を増やす。
- ガラス反射: 紫、短い虹色または白い縁を持つ。
- 2回反射: 金色、最も強い発光、得点価値が高いことを色以外にも太さで示す。
- ビーコン: 外側の柔らかい光、脈動する中間リング、白い中心、命中時に短く拡大する。
- 反射板（内部データ名はガラス片）: 半透明の紫青、中心線と外側の光を分ける、両端を印で光らせ、中央に反射方向を示す。プレイ中の案内では「光る線」と呼び、波が当たると向きが変わることを明記する。
- プレイ中の案内は、波を円、反射板を線、ビーコンを白い点の小さな記号で示す。ビーコンは波を重ねる対象であることも短く表示する。案内記号は表示だけであり、座標、判定、得点、経路台帳を変更しない。
- ヒット: 接触時に粒子と短い光を出し、画面へ「命中確認：」に続けてPERFECT / GREAT / GOOD / HITと、直接 / 壁反射 / 反射板 / 2回反射の種別を表示する。根タップ確定時の正の差分は「得点確定：+N」とし、新規件数、精度更新件数、発見済み件数、代表経路を1件へ集約して1.4秒表示する。加点0の既知経路は「発見済み（得点なし）」と表示する。表示した合計加点をHUDの増分と一致させる。

WebGLの `lineWidth` だけへ太さを依存させない。波は内側と外側を持つ帯として `TRIANGLE_STRIP` で描く方針を後続Phaseへ記載する。色だけで得点種類を伝えない。

## 音

音声ファイルまたはWeb Audio APIを利用してよい。容量だけを理由に、音を禁止しない。最低限の音候補は、タップ、壁反射、ガラス反射、ビーコン命中、2回反射命中、結果表示とする。初回のユーザー操作後に音声機能を有効化する。音が利用できない場合もゲームを止めない。音量設定を端末内へ保存できる仕様にする。

効果音は初期設定を「なし」とし、HOMEで「あり」へ変更した場合だけ鳴らす。ビーコン命中は得点計算に使う命中精度をそのまま利用し、次の4段階へ分ける。判定が良いほど音を高くし、音数を増やす。判定段階を追加しても得点式は変えない。

| 判定 | 命中精度 |
|---|---:|
| PERFECT | 0.85以上 |
| GREAT | 0.60以上、0.85未満 |
| GOOD | 0.30以上、0.60未満 |
| HIT | 0.30未満 |

壁反射とガラス反射は別音にする。2回反射で命中した場合は、命中判定の音へ短い追加音を重ねる。連続再挑戦や画面復帰で音を多重登録しない。

画面がバックグラウンドへ移った場合は、再生中と予約中の効果音を止め、音声機能を休止する。画面復帰時は、利用者が一度開始した既存の音声機能だけを安全に再開し、休止前の古い効果音を再生しない。開始・休止・再開に失敗しても、未処理エラーでゲーム進行を止めない。
